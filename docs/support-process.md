# Support process for maintainers

Updated October 4, 2026 · Build 1

This is maintainer guidance for handling public reports. It does not promise response times or a fix date.

1. Check the report for sensitive data. Do not copy it into another public artifact; use the private contact route when confidential details are needed.
2. Identify whether the problem concerns website behavior, location/source data or documentation. Keep the reporter's expected result separate from an independently reproduced observation.
3. Reproduce with a harmless case where practical. Record the page/code, browser or document version, steps, actual behavior and uncertainty. A report without a reproduction is still a report to investigate.
4. Keep implementation and deployment evidence in the appropriate private project. Public updates should describe the user-visible problem and verified outcome without exposing credentials, visitor data, host paths or unresolved exploit details.
5. State whether a change is proposed, locally validated or confirmed on the public website. Do not mark a deployed fix based only on a passing local test or a repository commit.
6. Link duplicate reports to the original. Explain the reason when resolving an issue; retain unresolved data/source questions instead of certifying a geographic claim from an agent's judgment alone.

Follow [the AI usage policy](https://loc.is/s/ai-policy.html) for new explanations, artwork, attribution and human review. A closed issue is not a certification of geographic accuracy, privacy or security.
